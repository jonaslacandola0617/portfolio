## Starting from a packet capture, not a textbook

I understood DNS "in theory" for a while before it actually made sense — what fixed that was
capturing a real lookup in Wireshark and reading the frames in order instead of reading a diagram.

## The resolution chain

<Mermaid chart={`
sequenceDiagram
    participant Client
    participant Resolver as Recursive Resolver
    participant Root as Root Server
    participant TLD as TLD Server (.com)
    participant Auth as Authoritative Server

    Client->>Resolver: Where is example.com?
    Resolver->>Root: Where is .com?
    Root-->>Resolver: Ask the .com TLD server
    Resolver->>TLD: Where is example.com?
    TLD-->>Resolver: Ask example.com's nameserver
    Resolver->>Auth: Where is example.com?
    Auth-->>Resolver: It's 93.184.216.34
    Resolver-->>Client: 93.184.216.34
`} />

In practice, most of this chain is cached — your resolver (often your ISP's, or `1.1.1.1` /
`8.8.8.8`) rarely has to walk all the way to root servers for a domain it has already resolved
recently.

## What it looks like in a capture

Filtering a capture on `dns` shows the query and response as two frames:

<CommandBlock title="Wireshark display filter" commands={["dns"]} />

The query frame carries the hostname and record type (usually `A` for IPv4). The response frame
carries the resolved IP address plus a TTL — how long resolvers are allowed to cache the answer
before asking again.

<Callout type="info" title="Why TTL matters for security work">
  A very short TTL is a signal used by some malicious infrastructure and by legitimate load
  balancers alike — DNS alone rarely tells you which, but it's one more data point in triage.
</Callout>

## Where this connects to the CIA triad

DNS underpins availability (can't resolve, can't connect) and, when unencrypted, doesn't provide
confidentiality — anyone on-path can see which domains you're resolving. That's part of the case
for DNS-over-HTTPS/TLS, which came up directly in the Google Cybersecurity coursework on network
security.

## Takeaway

Reading a DNS capture frame by frame took maybe fifteen minutes and taught me more than a week of
reading about it — a pattern that's held for most of networking so far: theory first, then watch
it happen.
