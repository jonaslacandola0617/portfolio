## Two models, taught for different reasons

The OSI model's seven layers are a teaching and design reference — a shared vocabulary for
describing *where* a problem lives. The TCP/IP model's four layers describe what the internet
actually runs on. You don't need to memorize OSI because devices literally implement it; you need
it because "that's a Layer 2 problem" is a faster sentence than a paragraph of explanation.

## The mapping

| OSI Layer | TCP/IP Layer | Example |
| --------- | ------------ | ------- |
| 7 Application | Application | HTTP, DNS, SMTP |
| 6 Presentation | Application | TLS encryption, encoding |
| 5 Session | Application | Session establishment |
| 4 Transport | Transport | TCP, UDP |
| 3 Network | Internet | IP, routing |
| 2 Data Link | Network Access | Switches, MAC addresses |
| 1 Physical | Network Access | Cabling, signaling |

## Where this actually helps: troubleshooting

<Callout type="tip" title="The habit that matters">
  When something breaks, work bottom-up: link light on? (L1) then MAC address learned? (L2)
  then can you ping the IP? (L3) then is the port open? (L4) then does the app respond
  correctly? (L7)
</Callout>

That order isn't arbitrary — a Layer 3 problem will always look like a Layer 7 problem to an end
user ("the website is down"), so ruling out the lower layers first prevents chasing application
logs for a routing issue.

## A concrete example from a lab

While debugging a broken inter-VLAN routing lab, "hosts can't reach each other" turned out to be a
missing `no shutdown` on a sub-interface — a Layer 1/2 issue wearing a Layer 3 costume. Checking
`show ip interface brief` first (interface status) before diving into routing tables saved a lot
of wasted time.

## Why both models still matter

Cisco material (and the exam) will reference OSI layer numbers directly — "a Layer 2 loop,"
"Layer 3 switching" — so fluency with both is less about theory and more about being able to
follow, and give, a precise diagnosis.
